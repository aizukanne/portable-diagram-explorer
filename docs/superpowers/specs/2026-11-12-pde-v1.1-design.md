# Part 1 — Spec

## 1. Problems, measured

### P1. There is no way to step through diagrams that no hotspot links

In a presentation, a viewer can reach a diagram only by clicking a hotspot. The viewer has no other
navigation: the root view shows `rootDiagramId`, and the modal opens only through
`Viewer.navigate`, which is called from a hotspot action (`src/ui/viewer.js:251-306`). The editor
already knows this. Its `W_UNREACHABLE` warning (`src/core/validate.js:188`) tells the author that
viewers cannot reach a diagram no hotspot leads to. A presenter who wants to walk a room through
diagrams in order has to add artificial hotspots, and some diagrams cannot be presented at all.
Raised by the owner on 2026-11-12.

### P2. SVG images are refused

`sniffImage` recognises PNG, JPEG and WebP only (`src/core/sniff.js:10`), and the schema's
`asset.mimeType` enum lists the same three (`src/core/project-schema.js`). Diagrams exported as SVG
from drawing tools have to be rasterised before import, which loses sharpness when zoomed. The owner
amended design decision D12 on 2026-11-12 to accept SVG.

### P3. Drill-down windows stay empty inside SharePoint/OneDrive's preview [#16]

Observed by the owner on 2026-11-12. When a shared `.presentation.html` is viewed in SharePoint's
in-browser preview, **the overview shows and the descriptions show, but clicking a hotspot opens a
window that stays empty.** From the owner's console capture, checked against the v1 build:

- `about:srcdoc:61` breaks SharePoint's policy (`script-src 'self' … 'nonce-e9c30c90-…'`). The
  blocked script's hash is `sha256-do+AvlM69A+eEtuIw2/h6BFIcWfVT4XtP8G9IM4jUAs=`. That is **the
  drill-down frame's own script**, the second hash in our presentation policy.
- `about:srcdoc:3124` ×6 breaks **our** policy (`'sha256-iR+dd0…' 'sha256-do+AvlM…'`). The
  hashes are not ours. The built presentation is 3,129 lines long, and its main script ends at line
  3125, so the preview loads **our presentation as a `srcdoc` document** and something adds six
  scripts at its end. Our policy refuses them, as designed.

**Working hypothesis (H1), not yet proven.** The preview gives our document SharePoint's policy and
puts SharePoint's nonce on our inline scripts, so our main script passes both policies and runs. The
drill-down frame is a `srcdoc` iframe that we create at runtime. It inherits both policies, but its
script carries no nonce, so SharePoint's policy blocks it. The frame never sends `READY`, and the
render times out after 20 s (`src/ui/bridge.js:13`). H1 explains every observation above, but only a
live check in SharePoint can confirm it (§5, live gate LG-1).

**Why v1 missed it.** v1 targeted a file opened by double-click (`file://`), and every browser test
runs that way. Being hosted inside another site's viewer was outside v1's scope.

### P4. A re-zipped package is refused (D11 amendment)

`readProjectZip` rejects any entry outside the allowed set (`src/core/package.js:141-146`). When
someone unzips a package and compresses it again in macOS Finder, Finder adds `__MACOSX/…` and
`.DS_Store` entries, and the package is then refused. Windows adds `Thumbs.db` and `desktop.ini` in
the same way. The owner amended D11 on 2026-11-12: skip these files and say which ones were skipped.

## 2. Scope

**In:**

1. A single running order of slides set by the author, with navigation in the presentation.
2. SVG images, displayed as pictures that cannot run anything.
3. Drill-down windows that work inside hosted viewers, plus a notice that suggests downloading the
   file.
4. Operating-system clutter in imported ZIPs is skipped and reported.

**Out:**

- Several named tours. *(owner)*
- Looping or kiosk mode. *(owner: "stop, say it's the end")*
- Timed auto-advance. *(agent call: not requested)*
- Repeating a diagram in the order. *(owner)*
- SVG interactivity: links, scripts and animation triggered by the viewer.
- Fonts or images that an SVG loads over the network.
- Detecting SharePoint by name. The fix is generic: it covers any host that applies its own policy.

## 4. Acceptance criteria

All criteria hold in Chromium, Firefox and WebKit, opened from `file://`, unless stated otherwise.

**Running order (P1)**

- A15. In the editor, the author adds diagrams to the running order, removes them and reorders them,
  by drag and by keyboard (Move up and Move down buttons). Each change is one undo step. Save and
  reopen keeps the order exactly.
- A16. In the presentation, Next and Previous step through the order, using the buttons, Right
  Arrow / Page Down and Left Arrow / Page Up. The counter reads "N of M", and the breadcrumb shows
  the slide title. The Next button and the Next keys do nothing on the last slide, which shows a
  "Last slide" marker; Previous does nothing on the first slide.
- A17. From inside a drill-down window three levels deep, Next closes the window and shows the slide
  after the last slide shown. Previous closes the window and shows the slide before it. Focus moves
  to the new slide's heading, and screen readers announce "Slide N of M: <title>".
- A18. The jump list names every slide in order, marks the current one, and is fully keyboard
  operable.
- A19. On a touch screen, a horizontal swipe on a slide at fit zoom moves to the next or previous
  slide. When zoomed in, the same gesture pans the diagram and does not change the slide.
- A20. A project without a running order behaves exactly as in v1: no slide controls are shown, and
  the v1 browser suite passes unchanged.
- A21. Deleting a diagram that is in the order removes it from the order. The delete confirmation
  says so, and undo restores both the diagram and its place in the order.

**SVG (P2)**

- A22. An SVG file imports and is listed as SVG. Its displayed size comes from the file's
  `width`/`height` or `viewBox`. An SVG with neither is refused, with a message naming the missing
  attributes and the fix.
- A23. An SVG containing `<script>`, event-handler attributes, `<foreignObject>` or external
  references imports with a **warning** that names what will not run or load. Nothing in it runs or
  makes a network request in the editor, the preview or the exported presentation; this is checked
  by the existing external-request listener and a `window.top` side-effect probe.
- A24. Hotspots on an SVG diagram line up with the drawing at 25%, 100% and 1600% zoom.

**Hosted viewers (P3)**

- A25. **Reproduction harness:** a host page that loads the presentation as `srcdoc` under a
  nonce-based policy, with nonce-stamped scripts (the H1 model). With the v1 build, the drill-down
  stays empty. With the v1.1 build, the drill-down renders inside the **sealed frame**.
- A26. **Fallback harness:** the same host page, but with the frame's script blocked by any means.
  Within the start-up deadline (§5.3), the drill-down renders **in the page** instead, and the notice
  is shown.
- A27. The notice appears whenever the presentation runs inside another page. It explains that the
  host is restricting the presentation and suggests downloading the file and opening it in a browser
  for the full experience. In fallback mode it also says that drill-downs are running with reduced
  isolation. It can be dismissed, and it does not appear when the file is opened directly or in the
  editor's own preview.
- **LG-1 (live gate, owner).** In the owner's SharePoint preview, drill-downs show their diagrams
  and the notice appears. The console capture is recorded in the acceptance report. Whether H1 or the
  fallback was the path taken is recorded too.

**ZIP clutter (P4)**

- A28. A package re-zipped by macOS Finder (with `__MACOSX/` and `.DS_Store`) and one re-zipped on
  Windows (with `Thumbs.db` and `desktop.ini`) both open. A warning lists every skipped entry by name.
  Any other unexpected entry is still rejected with `E_PKG_UNEXPECTED_ENTRY`.

**Compatibility**

- A29. A v1 package (`schemaVersion: 1`) and a v1 presentation both open in v1.1 unchanged. A v1.1
  file opened in the v1 editor gets v1's existing "made by a newer version" error, not a crash and not
  silent loss.

## 5. Success metrics

- The owner presents a talk from the running order alone, without making a hotspot for every step.
- LG-1 passes in the owner's SharePoint.
- The full browser suite stays green in all three engines. The A14 timings are re-recorded and are
  no worse than v1's.

# Part 2 — Design

## 5.1 Data model: schema version 2

Both additions change what a valid file contains. Because v1 rejects unknown fields
(`additionalProperties: false`), the schema version must change. **agent call**

- `schemaVersion` becomes `2`. Readers accept 1 and 2. A version 1 file is read as version 2 with
  no running order, and it is saved as version 2. The editor tells the author in one line on first
  save: "Saved in the v1.1 format; v1 editors cannot open it."
- A new optional top-level field records the running order:
  `sequence: { slides: [<diagramId>, …] }`. It holds between 1 and 500 entries, each ID must name a
  diagram, and duplicates are rejected with `E_SEQ_DUPLICATE` (the path and the repeated ID).
  A missing or empty sequence means no slide mode (A20). An empty array is normalised to "absent" on
  save, and the save says so (owner directive: no silent alteration).
- The `asset.mimeType` enum gains `image/svg+xml`.
- The presentation `formatVersion` becomes `2`, with the same rules: it reads 1 and 2.
- `W_UNREACHABLE` now counts the running order as a route: a diagram in the order is reachable.

## 5.2 Running order

**Editor.**

- The diagram sidebar gains a **Running order** section listing the slides in order. Each row has a
  drag handle, Move up, Move down and Remove.
- Each diagram's inspector gets an **Add to running order** / **Remove from running order** toggle.
- Diagrams in the order show a slide-number badge in the diagram list.
- When a project has no order yet, the first **Add** creates one with that diagram. **agent call:**
  the overview is *not* inserted automatically. This differs from the guess played back in chat; it
  is simpler and leaves the author's choice explicit.
- Every operation is one `edit()` step, so it is undoable under D10.
- `deleteDiagram` also removes the ID from the order, and the confirmation text names this (A21).

**Viewer — the state model.** `NavStack` stays exactly as it is for drill-downs. A small new
`SlideCursor` sits beside it. It is DOM-free in `src/core/` (D4) and unit-tested.

- `slides`: the ordered IDs.
- `index`: the slide last shown on the page, or `null` before the first slide is shown.
- `next()`, `previous()`, `jump(i)`, `isFirst`, `isLast`, and `label()` ("3 of 8").

**Opening a presentation.** It still opens on `rootDiagramId`, as in v1.

- If the overview is a slide, `index` is its position.
- If it is not, `index` is `null`. Next then goes to slide 1 and Previous is disabled. **agent call**

**Moving between slides.** Next and Previous replace the root view's scene with the target slide, as
`showRoot` already does for the overview. The root view's breadcrumb reads
"Slide N of M › <title>". If a drill-down is open, `closeModal()` runs first, without restoring the
pre-modal viewport, and then the slide changes (R3). For Previous from inside a drill-down, the
**agent call** mirrors the owner's Next ruling: the slide before the last slide shown.

**The modal's "Overview" button.** In v1 this button closes the modal and returns to the root view.
When the root view shows a slide that is not the overview, the button's label becomes **"Back to
slide"**. The page toolbar gains a **Home** control that shows the overview and keeps the counter in
step. **agent call**

**Controls (R6).**

- **Bottom bar:** ‹ Previous · "3 of 8" · Next ›, plus a **Slides** menu button. The menu reuses
  `ComponentMenu`'s keyboard and focus behaviour. It is rendered only when a running order exists.
- **Keys:** Right Arrow and Page Down mean Next; Left Arrow and Page Up mean Previous. They are
  ignored while focus is in a text field, a menu or dialog is open, or Alt is held, because Alt+Left
  remains Back (D18).
  - Inside the frame, plain arrows have no use in presentation mode today: `renderer.js:587` moves a
    hotspot with them only in edit mode. The frame therefore forwards them as `KEY` messages, and the
    D16 protocol whitelist gains the keys `Next` and `Previous`.
  - The Escape order (D18) is unchanged.
- **Swipe (A19):**
  - It applies only on the page, not inside drill-down windows (**agent call**: a swipe inside a
    window competes with panning a detail diagram).
  - It needs one pointer of type `touch` with the scene at fit zoom (`zoom ≤ 1.0001`).
  - It counts when the horizontal travel is at least 60 CSS px, at least twice the vertical travel,
    and the gesture takes under 600 ms. These thresholds are the builder's to tune by measurement.
  - When zoomed in, the existing pan behaviour wins.
- **Announcements:** "Slide N of M: <title>" through the existing live region. Focus moves to the
  root heading, following the A07 rule.

## 5.3 Hosted viewers (#16)

Two mechanisms, in order:

**1. Pass the host's nonce on (keeps the sealed frame; H1).**

- At start-up the main script reads `document.currentScript.nonce`. A script can read its own nonce
  through this property even though the attribute is hidden.
- If the nonce is non-empty, `FrameBridge` writes `nonce="<value>"` into the frame template's
  `<script>` tag before setting `srcdoc`. The value is validated against `^[A-Za-z0-9+/=_-]{1,200}$`;
  anything else is ignored.
- The frame's own hash policy still matches, because a nonce attribute does not change a script's
  hash. The host's policy now matches as well.
- This adds no new capability: the host already trusts our document with that nonce, and we pass it
  only to our own script, whose hash we pin.

**2. In-page fallback (when the frame cannot start).**

- `FrameBridge` gains a start-up deadline. If `READY` has not arrived within **T** ms of creating the
  frame, the bridge reports `startFailed`.
  - T is set by measurement in spike SP-2: the time to `READY` across the three engines at the A14
    envelope, under CPU load. T = max(3 × p99, 2000 ms).
  - `READY` is sent before any image is transferred, so T does not depend on diagram size. SP-2 must
    confirm this.
- On `startFailed`, the viewer switches to an `InPageScene` for the rest of the session.
  - `InPageScene` is a new class with the same interface as `FrameBridge`: `render`, `command`,
    `focus`, `focusHotspot`, `setTitle`, `destroy`. It wraps the `SceneRenderer` that the root view
    already uses in the page.
  - The pending render is replayed into it. The viewer code stays unaware of which one it holds.
- **What the fallback gives up:** the opaque-origin isolation of D16 for drill-down scenes. This is
  acceptable because the same project data is already rendered in the page by the root view, and all
  author text stays `textContent`-only under D19. SVG remains inert as an image. This trade is
  recorded as an amendment to D16. *Owner R8 accepts reduced isolation where the host forces it.*

**The notice (R8, A27).**

- A banner below the toolbar appears when `window.top !== window.self` and the viewer is not the
  editor's embedded preview. Text:

  > This presentation is being shown inside another site, which limits what it can do. For the full
  > experience, download the file and open it in your browser.

- In fallback mode it adds:

  > Drill-down diagrams are being shown with reduced isolation.

- **Dismiss** hides it for the session; the dismissal is not persisted.
- **agent call:** there is no Download button. In a hosted preview, the bytes of the current file are
  not reliably available to the page, and rebuilding them from the DOM is not byte-faithful (the
  reason for D6).

**Our policy and the host's scripts.** Our hash policy keeps refusing scripts that a host adds. That
is the security model working (D3), not a fault. The acceptance report will say so, so the console
lines do not look like a bug.

## 5.4 SVG (D12 amendment)

**Recognising an SVG.** `sniffImage` recognises SVG from its bytes:

- the text is UTF-8;
- after an optional BOM, whitespace, an XML declaration, comments and a DOCTYPE, the first element
  is `<svg` with the SVG namespace.

The test stays DOM-free (D4). `sniffFileKind` must check for SVG before its generic `<` → `html`
branch.

**Checking it, in the editor.** The browser layer parses the file with `DOMParser` (`image/svg+xml`),
which executes nothing.

- **Size:** from the root's `width`/`height` in px or unitless, otherwise from `viewBox`. If neither
  is present, the file is refused with `E_SVG_NO_SIZE`. The error names the attributes and gives a
  fix, for example `width="1200" height="800"`.
- **Warnings** (`W_SVG_INERT_PARTS`), listing counts of each:
  - `script` elements;
  - `on*` attributes;
  - `foreignObject`;
  - `href` and `xlink:href` values that are not `#fragment` or `data:`;
  - `@import` or `url(http…)` in styles.
- **Limits:**
  - an SVG file larger than 20 MiB is refused;
  - a file with more than 200,000 elements gets a performance warning. **agent call**, to be revisited
    with SP-1 data.

**Storage.** The bytes are stored unchanged, consistent with spec §10A, under the ZIP name
`assets/<id>-<slug>.svg`.

**Display.** Everywhere it appears, an SVG is shown as `<img src="data:image/svg+xml;base64,…">`.

- In an `<img>`, browsers render SVG with scripts disabled and no external loads. That is what makes
  it inert. The policy's `img-src data: blob:` already allows it.
- The renderer must take the scene size from the asset's `width`/`height`, never from `naturalWidth`,
  because SVG `naturalWidth` varies by engine. `assets.measure` likewise returns the parsed size for
  SVG.

**Spike SP-1 (before the SVG story).** In all three engines, measure an SVG in `<img>` under the
renderer's CSS transform at 25% to 1600% zoom:

- sharpness, which depends on whether the engine re-rasterises at scale;
- frame time while panning, on a 5,000-element and a 100,000-element drawing.

If an engine rasterises once and blurs, the renderer swaps in a re-rasterised `<img>` size at rest.
The spike decides this.

## 5.5 ZIP clutter (D11 amendment)

Before the allowed-entry check, entries are classed as clutter when the full name matches
`^__MACOSX/`, or the basename matches `.DS_Store`, or `Thumbs.db` or `desktop.ini` (the last two
case-insensitive), at any depth.

- Clutter entries are skipped and never decoded beyond the central directory. The D11 size and count
  limits still apply to them.
- One warning, `W_PKG_OS_FILES_SKIPPED`, lists every skipped name (the path is `(archive)`).

**agent call: a single wrapping folder.** Compressing an unzipped *folder* in Finder or Windows also
nests every entry under one top-level folder (`name/project.json`). When, after clutter is removed,
every entry shares exactly one top-level folder and `project.json` sits directly inside it, the prefix
is stripped and the same warning says so. Any other layout is unchanged from v1. This is the same
"re-zipped by an operating system" case the owner ruled on in R9.

## 5.6 Error handling

Every new rejection or alteration follows the house rule: a field path, the value received, the
accepted form, why it matters, a code, and a pointer to read more.

| Code | Where it comes from |
|---|---|
| `E_SEQ_DUPLICATE` | A diagram appears twice in the running order |
| `E_SEQ_UNKNOWN_DIAGRAM` | The running order names a diagram that does not exist |
| `E_SVG_NO_SIZE` | An SVG has neither width/height nor a viewBox |
| `E_SVG_TOO_LARGE` | An SVG file is over 20 MiB |
| `W_SVG_INERT_PARTS` | An SVG contains parts that will not run or load |
| `W_PKG_OS_FILES_SKIPPED` | Clutter files were skipped, or a wrapping folder was stripped |
| `I_SAVED_V2` | First save of a v1 file in the v1.1 format |

The fallback switch is announced by the notice, never silently.

  near-misses such as HTML that contains `<svg`); clutter classification and folder stripping; nonce

- **Browser (all three engines):** A15–A29, with harnesses A25 and A26 under `test/e2e/harness/`.

- **Regression:** the full v1 suite of 141 tests runs unchanged. The A14 envelope run is repeated and

## 5.8 Settled at builder check (2026-11-12, all agent calls)

An independent builder read this document and raised twelve questions. None needed an owner ruling.

1. **Host policy and the frame's style and image.** The owner's capture showed script violations
   only, with no style or image violations. Because the frame's script never ran, no image was ever
   posted, so the host's `img-src` is **unknown**.
   - The nonce is passed to the frame's `<style>` as well as its `<script>`.
   - If the host also blocks `data:` images, only the fallback can help. LG-1 will show which.
2. **Harnesses.** They are modelled on the exact `script-src` text from the capture in #16. There are
   **three** variants:
   - (a) nonce on our scripts: the sealed frame must render;
   - (b) no nonce on our scripts, with the frame blocked: the page must land in the fallback;
   - (c) the frame blocked by any means: the fallback renders.
   They extend the existing `harnesses[…]`/`hostCsp` mechanism in `build/build.mjs`.
3. **The protocol accepts SVG.** The D16 `RENDER_SCENE` image check in `src/core/protocol.js`
   accepts only `data:image/(png|jpeg|webp);base64`. S6 widens it to `svg+xml`, with a protocol unit
   test for both the accepted and the rejected forms. `InPageScene` does not use the protocol.
4. **Nonce read.** The main script reads `document.currentScript.nonce` synchronously, as its first
   statement, because `currentScript` is null after start-up. An empty nonce, as on `file://` and in
   the editor preview, means no change from v1.
5. **ZIP pass.** Clutter is classified first. Unexpected entries are still all collected in one pass,
   and the clutter warning is reported alongside any errors. Errors name the **original** entry path.
   The wrapping folder is stripped only if *every* remaining entry is under that one folder, so a
   top-level `project.json` next to `name/project.json` means no stripping.
6. **`I_SAVED_V2`** appears once per opened v1 file, on its first save. `README.txt` in the package
   states schema version 2.
7. **Previous with no slide shown yet**, when `index` is null, is disabled.
8. **Home** shows the overview and sets `index` to the overview's position in the order, or to null
   if the overview is not in it.
9. **Notice suppression.** The editor's preview builds the `Viewer` in-page with `embedded: true`.
   That flag suppresses the notice; `window.top` is not used for this case.
10. **SVG sizes.**
    - `px` or unitless values are used as given.
    - `pt`, `pc`, `in`, `cm` and `mm` convert by CSS absolute ratios.
    - `%`, `em`, `ex` and anything else fall back to `viewBox`; with no `viewBox`, the file is refused
      with `E_SVG_NO_SIZE`.
    - Values are rounded to the nearest integer, with a minimum of 1, because scenes require integers.
11. **Asset de-duplication and unused-asset checks** need nothing special for SVG.

## 8. Risks

| Risk | Mitigation |
|---|---|
| H1 is wrong: SharePoint does not put its nonce on our scripts | The fallback (V8) does not depend on H1. LG-1 records which path ran. |
| The host's preview also blocks `postMessage` or the iframe itself | The fallback needs neither. A26 blocks the frame by any means. |
| SVG blurs at high zoom in one engine | SP-1 runs before S6, and re-rasterising at rest is designed in. |
| Very complex SVGs are slow to pan | Element-count warning (V11). A14-style timing is part of SP-1. |
| The schema bump strands v1 editors | They give a clear existing error (A29). The editor travels inside every package (D6), so authors always have a matching editor. |
| The arrow keys clash with a host page | The keys are handled only while the presentation document has focus. |
