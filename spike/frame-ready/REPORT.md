# SP-2: time from iframe creation to the frame's first `READY` (refs #16)

## Result

**T = max(3 x worst p99, 2000) ms = max(3 x 1206, 2000) = 3618 ms.**

Worst p99 was 1206 ms (Firefox 157, "load" condition, warm samples; see table). T is a single start-up
deadline for all engines: if no valid `READY` arrives within T of iframe creation, the viewer falls back
to rendering in the page.

## Ordering confirmation

`READY` precedes any image transfer: `src/ui/frame-main.js:85` (`send('READY', {});`, the last statement of the
frame script) is the first message the frame sends, and the image bytes travel only in `RENDER_SCENE`
(`src/ui/bridge.js:107-108`), which `render()` holds back in `this.queued` until `READY` sets `this.ready = true`
(`src/ui/bridge.js:65`, `:102`).

## Method (`spike/frame-ready/measure.spec.mjs`)

- Page: `dist/test/viewer-fixture.presentation.html` (conditions a, b) or the A14 maximum-envelope
  presentation (condition c: 50 diagrams, 1000 hotspots, 49.4 MiB of images, 66.3 MiB file; generated by the
  existing `test/e2e/a14-envelope.spec.mjs` run with `PDE_A14=1`, then loaded from `test-results/a14/`).
- One sample = `window.__pdeViewer.bridge` is destroyed and nulled, a capturing `message` listener is added to
  `window`, `t0 = performance.now()`, then the viewer's own `openModal()` runs (it constructs a new `FrameBridge`,
  i.e. creates the `<iframe sandbox="allow-scripts" srcdoc=...>`). `t1` is the dispatch time of the first
  message with `type === 'READY'` from a window other than the page. Sample = `t1 - t0`; the harness also checks
  that the bridge's own validated `ready` flag is true, then closes the modal. No change to product code.
- WARM set: 50 destroy/recreate cycles in one already-loaded page (script/template caches warm).
- COLD set: first drill-down on a freshly loaded page, which is the real lazy path (the viewer keeps the bridge
  for the session). n = 20 fresh loads per fixture condition, n = 5 for A14 (66 MB loads are slow).
  With n = 20 or 5, "p95/p99" are effectively the largest or second-largest values; read them as maxima.
- Conditions: (a) idle; (b) "load": 4 busy Web Workers; (c) A14 envelope, idle. Extra (not in the brief):
  "saturated": 16 busy workers on the 8-thread host (oversubscribed).
- Workers: the presentation CSP forbids workers, so they run in a second page (`about:blank`) of the same browser
  context, which shares the engine's CPU with the measured page.
- Environment: headless Chromium 156.0.8078.80, Firefox 157.0, WebKit 27.2 (Playwright 1.64.1 container),
  software rendering, 8 hardware threads, shared dev host with other sessions' containers running (no isolation).

## How the load was verified

A busy-loop (400 ms, iterations counted) ran on the measured page's main thread before and while the workers
ran; every worker also posted its own iteration rate (all 4 / 16 reported). Throughput drop on the main thread:

| engine | 4 workers ("load") | 16 workers ("saturated") |
|---|---|---|
| chromium | -46.1% | -60.0% |
| firefox | -41.0% | -76.7% |
| webkit | -21.6% | -35.2% |

An earlier first pass of the 4-worker condition (not used in the table) showed a *negative* drop in Chromium
(-8.5%) and +8.3% in Firefox, i.e. that run did not demonstrably load the CPU (other host activity dominated);
it was discarded and re-run, and the drop above is what the table's "load" rows were measured under. The drop
varies between runs because the host is shared; treat "load" as "a measured 20-46% main-thread slowdown".

## Run-to-run variance

The idle condition was run twice (first run, then again at the end of the session):

| engine | warm p50 / p99, run 1 | warm p50 / p99, run 2 | cold p99, run 1 | cold p99, run 2 |
|---|---|---|---|---|
| chromium | 24 / 58.4 | 31.9 / 80.3 | 73.2 | 212.6 |
| firefox | 55 / 190 | 61 / 269 | 108 | 365 |
| webkit | 31 / 146 | 29 / 111 | 113 | 86 |

Medians repeat within roughly 10-30%; p99 and cold maxima vary by up to 3x between runs (shared host, n = 20),
which is why the table is not tighter than "tens of ms typical, a few hundred ms at the tail, one 1.2 s outlier".
The 1206 ms outlier is a single warm sample in one run (Firefox, 4 busy workers); the same condition's p95 was 153 ms.
Because p99 of 50 samples is the maximum, T already carries the 3x margin over that single worst observation.

## Reproduce

```
PDE_A14=1 scripts/e2e.sh test/e2e/a14-envelope.spec.mjs --project=chromium     # builds the envelope file
PW_CONFIG=spike/frame-ready/playwright.config.mjs scripts/e2e.sh               # idle, load, saturated
PDE_A14=1 PW_CONFIG=spike/frame-ready/playwright.config.mjs scripts/e2e.sh -g a14
```
(The spike config sets its own `outputDir` so Playwright's start-of-run wipe of `test-results/` does not delete
the envelope.) Raw samples: `spike/frame-ready/out/*.json` (git-ignored).
